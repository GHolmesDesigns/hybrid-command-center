00

Before you begin

If you have never started a program by typing a line of text, read this first. It is the one section that assumes nothing, and every later instruction is built on it.

Operator

What you are actually doing when you start this app

Hybrid Command Center has no icon to double-click. You start it by opening a text window called a terminal, pointing that window at the folder the app lives in, and typing one short line. The app then runs on your own computer and opens in your web browser like an ordinary website — except that nothing leaves your machine.

Every instruction in this manual is that same loop: point a terminal at the folder, type a line, press Enter, wait. Learn the loop once, here, and the rest of the manual is only ever telling you which line to type.

The eight words that appear on every page

Terminal
A window where you type instructions instead of clicking them. On Windows it is called PowerShell or Windows Terminal. It looks more dangerous than it is: it does nothing at all until you type something and press Enter.
Command
One line you type into a terminal. In this manual commands are printed in a monospaced box, like npm install. Type them exactly, spaces included.
Folder path
The full address of a folder, written out as one line — for example C:\Users\you\Documents\hybrid-command-center. It is the same folder you would click your way to in File Explorer, written as text so a terminal can understand it.
The app folder
The one folder that holds this whole application. You can recognise it: it directly contains a file named package.json and folders named client and server. Almost every problem in Section 09 comes from running a command somewhere else.
Node.js
The engine this application runs on, the way a spreadsheet needs Excel. You install it once from nodejs.org and then never think about it again.
npm
Short for Node package manager. It arrives with Node.js and it is the program you are talking to whenever a command starts with npm. Its job is to fetch the pre-built parts this app is assembled from, and to run the app's named shortcuts — npm run dev is a shortcut, not a separate program.
node_modules
The folder npm creates the first time you run npm install. It holds those pre-built parts. It is large, it is not your work, and it is rebuilt from scratch by running npm install again. Never back it up and never edit it.
.env
A plain text settings file that sits in the app folder and holds this machine's private values, such as Google keys. The leading dot is part of the name. It is never shared and never published.

The one skill that matters: opening a terminal in the right folder

A terminal is always “standing in” one folder, and it runs your command there. Point it at the wrong folder and a perfectly correct command fails. Do this on Windows:

  1. Open File Explorer — the yellow folder icon on the taskbar, or hold Windows and press E.
  2. Click your way to the app folder. You are in the right place when you can see package.json, client, and server listed inside it. If you do not know where it was put, ask whoever set the machine up and write the path down in the box below.
  3. Right-click a blank area inside that folder and choose Open in Terminal. If that choice is not on the menu, click once in the white address bar along the top of the window so the path highlights, type powershell over it, and press Enter.
  4. A window opens with a line of text ending in >. The text before the > is the folder you are standing in. Read it and confirm it is the app folder.
  5. To be certain, type dir and press Enter. You should see package.json, client, and server in the list. If you do not, close the window and start again at step 2 — do not type anything else.
On a Mac or on Linux

Open Terminal from Applications → Utilities. Type cd, then a space, then drag the app folder from Finder onto the Terminal window — it pastes the path for you — and press Enter. Use ls where this manual says dir. Every npm command in this manual is identical on all three systems.

Typing a command, and knowing when it is done

  • Type the line exactly as printed, or copy it from this page and paste it — right-click pastes into PowerShell. Then press Enter once.
  • Text will scroll past while it works. That is the command reporting progress, not an error. Yellow warnings during npm install are normal and can be ignored.
  • Do not close the window while a command is working. Wait for one of the two endings below.

There are only two kinds of command in this manual, and they end differently:

Kind Examples How you know it worked
Does a job, then stops npm install, npm run db:migrate, npm run db:backup The scrolling stops and the > prompt comes back, waiting for you. You can now type the next command or close the window.
Keeps running until you stop it npm run dev, npm start The prompt never comes back and a web address is printed. That is success, not a freeze. Leave the window open and go use the app.

To stop a running app: click the terminal window, then hold Ctrl and press C. Closing the window stops it too. Minimise that window while you work — do not close it, or the app shuts down mid-sentence.

Write these down once

Fill these in the first time someone sets this machine up, and this manual becomes a great deal shorter to use.

What Where to find it Value for this machine
App folder path The address bar in File Explorer while the folder is open
Everyday web address Printed by npm run dev; normally localhost port 5173
Who to ask The person who installed it, for anything in the Engineer lane

Localhost is the name a computer uses for itself. A web address beginning http://localhost is served by your own machine and is not on the internet. Nobody else can open it, and the address will not work on your phone.

You cannot damage client files from here. Every command in this manual acts on this app's own folder and its own local records. None of them delete, move, or overwrite anything in Google Drive. The worst an ordinary mistake does is refuse to run and print a message.

You are ready for Section 02 when you can open a terminal that is already standing in the app folder, and dir lists package.json.

01

Orientation

What this application is, what owns which data, and the boundaries that hold the rest of the manual together.

Operator

One studio, one operator, one source of truth

Hybrid Command Center is where your clients, projects, tasks, deadlines, and planned social content live. Normally it runs on your own computer and is reached through your browser at an address only that computer can serve. It can also be published to one private web address with a single login, and from 5.4.2 signing in from a second machine is a supported, tested step rather than an accident. Even then it is one workspace for one person: there are no team accounts, and no copy of your records travels between machines.

Two places hold your work, and they never overlap:

  • Your computer keeps the records — clients, projects, tasks, checklists, dependencies, notes, tags, and planned posts. All of them sit in one file, which is why Section 08 exists.
  • Google Drive keeps the actual files. The app stores links to Drive folders, never copies of your documents.

Deleting a project or a task here never deletes anything in Drive.

Reaching it from a second machine

Only possible once an engineer has published the workspace to a private web address; it is not something you can switch on yourself. Once they have, there is nothing to install on the second machine. You open the same address in a browser, sign in with the operator password, and you are looking at the same live workspace, not a copy of it. Close the laptop and the second machine still works, because the records live on the host rather than on either computer.

Once the hosted copy is live, stop opening the local one. The npm run dev workspace on your own machine does not know the hosted one exists. Enter a client in one and it will never appear in the other, and there is no merge that will reconcile them afterwards. The moment an engineer declares the host authoritative, the laptop becomes a cold spare you keep for emergencies and do not type into.

What it deliberately does not do

There are no team accounts, no client portals, no billing, no time tracking, and no permissions. If you need those, this is not the tool that will grow into them.

Engineer

React 19 front end, Express 5 API, node:sqlite store

client/     React + TypeScript + Vite; typed HTTP boundary in src/api.ts
server/     Express local API
  domain/   deadline and dependency rules, framework-free
  drive/    read-only browse, confirmed writes, agent approvals, media resolution
  signal/   SignalProvider (read), service.ts (writes), campaigns, queue-health
  publish/  Post Bridge + Buffer providers, inventory, analytics
  mcp/      stdio + authenticated HTTP, tools, resources, prompts, work sessions
  agent-coordination/  handoffs, leases, notes, retained audit events
  app.ts    validated HTTP endpoints        db.ts  SQLite schema
shared/     cross-layer types, workflow constants, branding defaults
e2e/        Playwright critical-flow coverage
data/       gitignored SQLite database and backups

The browser never receives Google tokens. UI code calls only the local API. Every outside system sits behind a narrow provider interface: DriveProvider for browsing, DriveMediaProvider for one resolved media link, SignalProvider for reading the schedule, AnalyticsProvider for figures, and separate provider interfaces for confirmed Drive writes, Buffer reads and writes, and provider inventory.

Timestamps are stored as UTC ISO strings. Date-only deadlines are interpreted in the machine's local timezone and become overdue after that local calendar day has passed.

The checklist decides authentication, not the bind address. Operator auth turns on when the complete authentication checklist is present — a session secret, operator password hash, HTTPS origin, TLS termination acknowledgement, and an explicit trusted-proxy setting — and it stays on even when HOST remains 127.0.0.1. That matters because the supported AWS package keeps Node on loopback behind same-origin Caddy: leaving loopback is not what gates login. A local npm run dev without the checklist stays passwordless, and a non-loopback HOST is still refused until the checklist is complete.
Agent

Invariants that outrank any local convenience

  • client/ never imports a Google SDK and never reads a secret.
  • server/drive/browse.ts is the read-only half of Drive and stays that way. Folder creation and uploads live in the separate confirmed write path. Each write names its exact target and action, is hash-checked against its preview, and records an audit event. Downloads, moves, renames, and deletes remain unavailable.
  • SignalProvider has no write method by construction. Adding one means a new module beside read.ts.
  • The calendar reads and never writes. Scheduled content and task due dates stay two kinds — two arrays, two headed groups, never one list of "events" with a type tag.
  • Figures are read, never computed, never written back. AnalyticsProvider has sync, list, and days and no way to submit, update, or cancel.
  • Queue health is derived, never stored. There is no alerts table.
  • Keep deadline and dependency rules out of React components.
Widening one interface must not widen another. DriveProvider and DriveMediaProvider are two interfaces on purpose. Files receives DriveProvider and cannot reach the media path at all.
02

Install and first run

Getting from a copy of the files to a working application on this machine. Google Drive can wait; this part cannot.

Operator

Set it up once, then start it in one command a day

This section assumes you can open a terminal that is already standing in the app folder. If that sentence is not yet obvious, read Section 00 first — it takes five minutes and it is the thing that makes the rest work.

First, install the engine

  1. Go to nodejs.org and download the version marked LTS, as long as it is 24 or newer. Run the installer and accept every default.
  2. Close every terminal window you have open, then open a new one. Windows only notices newly installed programs in windows opened afterwards. Skipping this one step is the most common reason a correct command answers npm is not recognized.
  3. Check it took: type node --version and press Enter. A version number such as v24.4.0 means you are ready. An error means the installer did not finish, or you are still in an old window.

Then, the four setup commands

Run these once, in this order, in a terminal standing in the app folder. Wait for the > prompt to return before typing the next one.

Type this What it does What you should see
npm install Fetches the pre-built parts the app is assembled from and puts them in node_modules. Several minutes of scrolling the first time, then the prompt returns. Yellow warnings along the way are normal.
Copy-Item .env.example .env Makes this machine's own settings file by copying the blank template beside it. No output at all. Silence is success here. A file named .env now sits in the folder.
npm run db:migrate Builds the empty local database that will hold your clients, projects, and tasks. Database schema is up to date.
npm run dev Starts the application and keeps it running. A web address is printed and the prompt never returns. That is success. Open http://localhost:5173 in your browser.
On a Mac or on Linux

Every command above is identical except the second one, which is cp .env.example .env. Everything else, including the web address, is the same.

Every day after the first, only the last command matters. Open a terminal in the app folder, run npm run dev, and open the browser. The other three are setup, not routine. Run npm install again only when someone tells you the app's files have been updated.

Stopping, and leaving it running

Keep that terminal window open the whole time you work — minimise it, do not close it. To stop the app deliberately, click the window and hold Ctrl while pressing C. Closing the window stops it too, which is fine at the end of the day and disruptive in the middle of one.

Empty workspace, or something to look at first?

To start clean, do nothing more — go and create your real clients. To have something to explore before you commit, run npm run db:seed before you enter anything of your own. It creates three example clients with projects, tasks in every column, overdue work, a checklist, and a blocked task, and it never contacts Google Drive.

Seeding refuses to run once a single real client exists, so make the choice before you start typing real work.

Opening the settings file when you need to

Windows has no default program for a file called .env, so double-clicking it will ask you to choose one. Right-click it, choose Open with → Notepad, and tick nothing about always using Notepad. Inside, each line reads NAME=value. Change only what a section of this manual tells you to change, save, and restart the app for it to take effect.

If it refuses to start and prints a list of settings, read the list rather than the first red line. Each entry names one setting in .env and what was wrong with it. It never prints the value it rejected, so the message is safe to copy and send to an engineer.
Engineer

Commands, ports, and boot validation

npm install
cp .env.example .env
npm run db:migrate
npm run db:seed      # optional local demo data, never touches Drive
npm run dev          # Vite 5173 + API 8787, live reload

Production-style local run: npm run build then npm start, served from http://localhost:8787 alone. Rebuild after code changes.

For a hosted operator, generate the Argon2id password hash with npm run auth:bootstrap and follow docs/cloud-hosting.md and docs/cloud-cutover-rehearsal.md. Do not expose the development server or improvise a public bind.

Every .env variable is validated at startup against a Zod schema. A refused value stops the boot with every problem listed at once, naming the variable rather than echoing the value. Blank and absent are the same thing: the documented default applies.

Changing PORT is rarely worth it — the OAuth redirect URI and the dev proxy both have to move with it. Closing the duplicate process is usually the real fix for a port collision.

Drive is genuinely optional. Leave all three Google values blank and the app runs with Drive reporting itself unconfigured. A value that is present has to be usable.
Agent

Test and script constraints

  • npm run db:seed creates local demo records only and must never contact Drive. --with-drive is the explicit opt-in and exits without changes if clients already exist.
  • npm run signal:import loads real archived campaign content, idempotent by post id, never overwriting an existing post. It is not part of db:seed because it is content, not demo data.
  • Automated tests use the mock provider and must never call real Drive.
  • Playwright starts and stops the API and Vite itself on ports 8788 and 5174 against data/e2e.db, deleted at the start of every run. If the command does not exit on its own, something it spawned outlived the run — that is the bug.
  • Specs share one server and one database and run one at a time. Scope any count assertion to rows the spec created, or read the number back from the API in the same run.
Owner-run only, never in CI: npm run probe:post-bridge --live writes to real social accounts. It refuses to start without an API key, --yes, --accounts-approved, an instant at least 48 hours out, an unused --probe-label, an explicit --account <platform>:<id> per account, and the label typed back at the prompt. Hard budget of 50 requests including cleanup.
03

Connecting Google Drive

Optional. Do it before you create real clients if you want their Drive folders built for you automatically.

Operator

Giving the app permission to use your Drive

Google will not let a program touch your Drive just because you ask it to. The permission has to be registered with Google in advance, and Google Cloud Console is the website where you register it. It is free for this, it is a separate site from Drive, and it looks like a developer tool because it is one. Budget about fifteen minutes. You do this once, ever.

Sign in with the right Google account first. Whatever account you are signed into at console.cloud.google.com is the Drive this app will use. If the studio has a separate work account, sign out of your personal one before you start. Getting this wrong is the single most common failure, and unpicking it means starting over.

What Google calls things, and what they mean here

Project
In Google Cloud, a container that holds a set of settings. It has nothing whatever to do with projects in this app. Make one, name it something like hybrid-command-center, and forget it.
API
A single Google service you are switching on. You need two of them: the Drive API so the app can make folders, and the Picker API so you can choose a folder from a proper Google file-picker window.
OAuth consent screen
The page you yourself will see later when you approve the app. Google makes you write it before it will show it to you.
Client ID and client secret
A username and password belonging to the app, not to you. You copy them into .env and never type them anywhere else.
Redirect address
Where Google sends your browser back to once you have approved. It has to match what the app expects, character for character.

In Google Cloud Console, in this order

  1. Create a project, or select one you already made for this.
  2. Go to APIs & Services → Library, search for Google Drive API, and enable it. Search again for Google Picker API and enable that too.
  3. Fill in the OAuth consent screen. Choose External and leave it in Testing. On the test-users step, add your own Google address — the same one you are signed in as. Without that, Google will block you from your own app.
  4. Go to Credentials, choose Create credentials → OAuth client ID, and pick the type Web application.
  5. In Authorised redirect URIs, add the address below exactly as printed. No trailing slash, no https, no capital letters. 
    http://localhost:8787/api/drive/oauth/callback
  6. On the same screen, under Authorised JavaScript origins, add both of these. Miss this and Drive itself will still connect, but the Picker fails with Access blocked — no registered origin and Error 401: invalid_client. 
    http://localhost:5173
http://localhost:8787
  7. Google now shows you a client ID and a client secret. Copy both somewhere safe before closing that box — the secret is easy to lose and awkward to replace.
  8. Still under Credentials, create an API key for the Picker, and note the project number shown on the console dashboard.

Back on your own machine

  1. Open .env in Notepad, as described in Section 02. The lines you need are already there and empty. Paste each value straight after its = sign — no quotation marks, no spaces on either side of the =.
    Line in .env What goes after the =
    GOOGLE_CLIENT_ID The client ID from step 6. It ends in .apps.googleusercontent.com.
    GOOGLE_CLIENT_SECRET The client secret from step 6.
    GOOGLE_API_KEY The API key from step 7.
    GOOGLE_APP_ID The project number from step 7 — digits only.
    GOOGLE_REDIRECT_URI Already filled in for you. Leave it exactly as it is; it has to match what you typed into Google in step 5.
    GOOGLE_TOKEN_ENCRYPTION_KEY Not from Google. Invent a long random string of at least 32 characters — a password manager's generator is ideal.
    Keep a copy of that encryption key somewhere private and separate from your backups. Section 08 explains why the separation matters.
  2. Save the file. Stop the app with Ctrl+C and start it again.
  3. In the app, open Settings → Google Drive → Connect Google Drive. Read the Google approval page, confirm it names the account you intended, and approve.
  4. Choose Select root folder with Google Picker and pick the one Drive folder that will hold everything this app creates. Pasting a folder address instead will not work — picking it in that window is what actually grants access.

Three fields, three formats

Google asks for the same addresses three times in three shapes, and a value that is right in one box is rejected in the next. This is the single most common reason Drive setup stalls.

Where Shape Example
Authorised redirect URIs Full path http://localhost:8787/api/drive/oauth/callback
Authorised JavaScript origins Origin only — no path, no trailing slash http://localhost:5173
API key → Websites Wildcard http://localhost:5173/*

Both ports appear because npm run dev serves 5173 and npm start serves 8787. List only one and the Picker breaks whenever you switch between them.

What the status on a card is telling you

Drive ready Drive pending Drive issue Drive offline

Ready: the folder exists. Pending: setup is unfinished or still needs a nudge. Issue: Google returned an error. Offline: Drive is not connected at all. In every one of those cases the client, its projects, and its tasks carry on working normally — only the folder link is affected.

Drive stops working after about a week? Nothing is broken. An External app left in Testing is given permission that Google expires after seven days. Reconnect from Settings whenever it lapses, or ask an engineer to take the app through Google's publishing and verification process so it stops expiring.
Engineer

Token handling and root-folder resolution

GOOGLE_TOKEN_ENCRYPTION_KEY must be at least 32 characters. It is hashed into the key that encrypts OAuth tokens at rest, so a short one is accepted by the cipher and protects nothing. Back it up separately from the database — a backup of one without the other restores nothing usable.

Rotating the encryption key does not revoke an already-issued token. Revocation happens on Google's side.

The app requests only drive.file: it can use files it created and folders the operator explicitly selected. Google Picker is the grant path for an existing root; pasting a URL alone cannot grant access. Picker also verifies a stable folder ID and refuses files or trashed folders.

Provisioning behaviour

Folder creation is resumable and idempotent: successful steps persist, and a retry picks up where it stopped. A client gets a folder under the root; a project gets a folder and five standard subfolders. A local project rename does not rename the Drive folder.

Agent

Drive rules

  • Never commit .env, OAuth credentials, encryption keys, tokens, SQLite files, or logs.
  • Tokens are encrypted server-side and never returned to the browser.
  • Drive is authoritative for files; SQLite stores only references and provisioning metadata.
  • Identify Drive folders by ID and stable idempotency properties, never by name alone.
  • Persist successful partial steps and make retries safe. Never mark Drive connected before every required step succeeds.
  • Do not rename a Drive folder after a local rename without an explicit confirmation flow.
  • Never delete or modify a Drive file as a side effect of a local delete.

The Files module browses a project only at its own Drive folder and the subfolders drive_steps recorded for it, matched by ID. Any other folder ID is refused rather than fetched.

Create folder and Upload file are separate confirmed capabilities beside browsing. Preview the exact name, destination, size, MIME type, and content hash, then confirm that unchanged plan. Files still cannot download, move, rename, or delete anything in Drive.

Agent Drive-write approvals

The optional drive:write-request scope lets an agent request only a folder creation or a bounded upload. It does not execute the write. Review the exact action, target, agent label, request time, content metadata, and confirmation text in Agents → Drive write requests, then approve or deny it yourself.

  • The global pending queue is limited to 20 requests and 50 MiB decoded upload data.
  • One upload is limited to 10 MiB; a pending request expires after 24 hours.
  • An approval executes immediately under a one-hour lease.
  • A timeout or abandoned lease becomes Provider outcome is uncertain. Never retry it blindly: inspect the exact Drive folder and activity first because Google may have accepted the write.
  • Terminal rows retain metadata and evidence but purge upload content. The card shows pending count/bytes, oldest pending age, expired count, and uncertain count.
04

Your first working session

Client, then project, then task — the order that produces the cleanest workspace.

Operator

Seven steps end to end

  1. Create a client. Clients → New client. Only the name is required.
  2. Create a project under that client. Add description, status, priority, dates, deadline, and categories as needed.
  3. Create a task. The last project you opened is pre-selected; the client follows from the project. Pick a Type — Blog Post, Video, Social Post, Graphics, Scheduling, QA / Brand Pass, Admin, Dev Work, or Other — or leave it on No type, which is perfectly normal.
  4. Add a checklist. Open the task, type an item, select Add. The card then shows progress as a fraction, such as 2/4.
  5. Add tags. Type a name and press Enter or a comma. Existing names appear as suggestions.
  6. Add a dependency on the task that must wait. It shows Blocked until every dependency is complete, and the detail view lists what is holding it up.
  7. Move work through Status by dragging a card, or with the status selector at the bottom of the card, which is the keyboard route. Position saves automatically.

The five stages are fixed in this version: Backlog, To Do, In Progress, Review, Complete.

Capitalisation never creates a second tag. brand system, Brand System, and  Brand  System  all attach the one existing tag and keep its stored spelling. The same is true of project categories and Signal campaigns.

Trying to complete a blocked task is explained rather than silently refused. Finish the dependencies, remove an incorrect one, or confirm the override deliberately.

Engineer

The shape of the data

Clients own projects; projects own tasks. Board-card and project-tile positions persist, so drag order survives a reload. Dashboard counts and board filters are computed from one shared rule, which is why they always agree.

Labels are normalized joins, never packed columns: tags label tasks, categories label projects, Signal campaigns label Signal posts. All three match names case-insensitively through one shared rule in shared/types.ts. Renaming a label is a single write; deleting one detaches it and never deletes what it was attached to.

Deadlines

Next 7 days includes today, so a task due today appears under both counts. Completed tasks are never counted as overdue. Work under an archived project or client drops out of every dashboard count and list, but stays visible on the board and at its direct link.

Recently updated follows the work: adding, editing, completing, or deleting a task, ticking a checklist item, or changing tags or dependencies all move a project up. Rearranging tiles is not work and changes nothing there.

Agent

Deletion, archival, and merge semantics

  • Archive rather than permanently delete top-level clients. Projects and tasks may be hard-deleted from SQLite on user confirmation.
  • A project delete cascades to its tasks and leaves Drive untouched.
  • Merging a client moves its projects, archives the source, records it in client_merges as an alias of the survivor, and retargets earlier aliases so every lookup stays one hop.
  • The merge chooses field by field over exactly six columns — name, contact_name, email, phone, website, notes — each defaulting to the survivor's own value whether or not it is blank. Inferring from blankness would make the merge decide which record is current.
  • status and every drive_* column are outside the choice. slug derives from the surviving name through buildClientSlug, the same rule a rename follows.
  • The plan carries both records' values and every chosen one, so the confirmation hash covers them: a preview taken under other choices cannot be confirmed.
  • A merge touches no Drive folder and writes no integration_events row.
There is no undo on a merge. It is one transaction, previewed and confirmed.
05

The modules

Ten places to be. Each one is labelled with what it is allowed to do to your data.

Operator

Where each job lives

Ten areas, reached from the sidebar. The tag beside each name says what it is allowed to do: READ only shows you things, WRITE changes them, and READ ONLY means the area physically cannot alter what it is showing you, however hard you click.

Dashboard READ

Start here. Overdue, due today, next seven days, and project health. Every count is a link to the board filtered behind it.

Clients READ / WRITE

Search, edit contact details, open Drive folders, review connection state, archive, and merge duplicates.

Projects READ / WRITE

Search, filter by client and category, seven sort modes, plus a Custom order you arrange by drag or keyboard that persists.

Status READ / WRITE

The five-stage board. Filters for client, project, priority, task type, focus, and tags are all written into the browser's address bar, so you can bookmark a filtered view or send it to someone.

Signal READ / WRITE

The planner for content: month grid, unscheduled queue, quick capture, and the full editor for channels, media, timing, and campaigns.

Import WRITE

Turns a campaign planning spreadsheet, or tab-separated text pasted straight in, into a client with its projects, tasks, checklists, and dependencies. It shows you everything it intends to create before it creates any of it.

Files READ / CONFIRMED WRITE

Browse a project's Drive folder. Type, size, and modified date on every row, with Open in Drive. A separate preview-and-confirm flow can create a folder or upload a file; downloads, moves, renames, and deletes remain unavailable.

Calendar READ ONLY

A month agenda putting scheduled content beside task due dates, kept as two groups rather than one merged list.

Agents READ / CONTROL

Set up local or hosted MCP connections, issue scoped credentials, verify connection health, review handoffs and leased work sessions, and approve or deny agent-requested Drive writes.

Settings READ / WRITE

Drive connection, branding, tags, categories, and campaigns. Deleting a label tells you how many records it affects and never deletes one of them.

Branding is yours to change. Settings holds the sidebar wording, colours, and an optional logo, and refuses a combination that would be unreadable — contrast is checked as you type. Every field resets to the studio default.

Integration activity is an append-only record of what each integration changed, bounded to the most recent 200 rows, credential-scrubbed, and shown on the Import page beside the receipt it belongs to.

Agent

Module-level rules

  • Files browsing remains read-only. Its separate confirmed-write service may create folders and upload files after an exact preview; it cannot download, move, rename, or delete.
  • Branding validates from one place. brandingIssues, sidebarPalette, and shared/contrast.ts are used by both the API and the form. Never validate branding on one side only.
  • An import previews before it writes, plans from the same code twice — once for the preview, once against the workspace as it stands at the commit — and writes the whole hierarchy in one transaction. It skips a record the workspace already has, reports the rule that matched, and never edits one.
  • Changing what the importer does means changing docs/campaign-playbook-import-format.md in the same branch.
  • Every integration operation that changes local data records one integration_events row through recordIntegrationEvent, in the same transaction as whatever else it persists. Report PARTIAL whenever some of an operation landed and some did not, and name what landed.
  • Never write a credential to the log. Pass structured fields, not a request or response dump, and let redactSecrets scrub the one free-text field an external failure reaches.
  • Signal's own writes record no integration_events row — it is local data now, like projects and tasks. The log is for what an integration did.
  • Pair visual status colours with text or icons, and preserve visible keyboard focus.
06

Publishing and figures

Signal Campaign plans content. Publishing submits it. Figures read what the platforms report back. All three stay separate on purpose.

Operator

Plan it here, preview it, then confirm

Two words in this section carry the weight. The provider is the outside service that actually delivers a post to Instagram, LinkedIn, and the rest; this app plans and hands over, it never publishes directly. Figures are the view and engagement numbers those platforms report back afterwards.

Nothing is sent and no outside service is contacted until you press a button that says so. Save the post and any per-platform wording first, then choose Show preview.

Reading the preview

The preview opens with every channel in one short list — Ready to send Blocked Not available from this provider — naming the account each one matched to, so you can catch a post aimed at the wrong profile before it leaves. Blog is always last: no provider publishes to a blog, so post it yourself and then mark it published here.

Below that is one tab per destination showing exactly what that account will receive: the text, a marker beside anything you overrode for that platform, the title and first comment, the media in that account's order, and the date and time both in your own timezone and as the exact moment the provider will be given. The tab also says whether the provider sends the post itself or hands it to the platform's phone app for you to finish by hand.

Why a warning sits on one channel rather than the whole post

Limits are almost never true of a post as a whole. A caption over 280 characters stops X and is perfectly fine on LinkedIn, so the warning belongs to X. Every refusal says what has to change, and all of them have to be cleared before Confirm and submit will do anything.

Video never plays by itself in the preview — press Load this video. A file held in Google Drive is listed by name, type, size, and when it was last checked rather than shown, because a Drive link points at a page about the file, not the file itself.

A result marked UNCONFIRMED means nobody knows whether it went out. The app will never quietly try again, because that is how the same post ends up published twice. Open Post Bridge, find out what actually happened, and only then decide what to do.

Four things that never happen on their own

  • Mark published is always your decision. A successful delivery does not move the post's planning status for you.
  • Mark finished on a hand-delivered post records that one delivery only, not the whole post.
  • Figures change nothing at all. No number a platform reports can move a post, alter a schedule, or change a delivery result.
  • Figures refresh only when you press refresh, and a failed refresh leaves the last good numbers on screen rather than blanking them.

A channel this provider does not measure says Not available from this provider instead of showing a zero. Those are two different claims and only one of them would be true.

Engineer

Enabling the provider path

Publishing is off until both POST_BRIDGE_API_KEY and an explicit IANA PUBLISH_TIMEZONE (for example America/New_York) are in .env. The API key stays on the server and is never returned to the browser, written to the database, or written to the activity log.

Delivery state is deliberately separate from the planning status PUBLISHED. The boundary, the content-variant inheritance, and the scheduling conversion are recorded in docs/publishing-integration.md.

Deleting a post with a live provider submission cancels it first; publication history then protects the Signal post from deletion so the audit record stays readable.

Figures

server/publish/analytics.ts writes only signal_post_metrics, signal_post_metric_days, its own connection record, and one integration_events row. Every provider read completes before any write, so a refusal or failure cannot clear a good value. A per-day gain is a subtraction between two stored snapshots.

Campaign totals add the provider's own per-delivery figures over a named set. server/publish/campaign-analytics.ts holds no provider and makes no network call, so opening a campaign view can never spend a synchronisation.

Agent

The media boundary, stated exactly

This app stores no media files, serves no media bytes, and holds no media bytes at rest.

  • server/drive/media.ts resolves one user-supplied Drive link — parsed as a URL and host-checked before anything is looked up — to canonical metadata and a version fingerprint, without reading bytes.
  • Its separate confirmed byte path streams that same file straight to the provider's upload URL during a confirmed submit, update, or restore-and-resubmit, persisting nothing and never writing to Drive.
  • Neither half is available to Files. There is no byte method on browse.ts or shared/drive.ts.
  • A provider media ID is ephemeral: never a durable Signal reference, recreated on every submit, update, and restore-and-resubmit.

A media reference is discriminated

A row in signal_post_media is a public https: URL or a Drive file, never something in between. The rule is one function, signalPostMediaIssue in shared/signal-media.ts, enforced at the Zod boundary, in the write service, and by SQLite triggers — a rule stated in one layer is one the next INSERT walks around.

A Drive row carries Drive's name, MIME type, size, and at least one version signal, because a file ID is not evidence of the bytes anyone previewed: Drive may replace a file's content under the same ID. Classify with signalMediaKindFor, never by passing a Drive row's URL to signalMediaKind.

A preview makes no Drive call — preflight reads the stored MIME type, and the plan hash covers the whole descriptor and fingerprint, so a file that moves invalidates a plan taken before it did. A stored fingerprint is replaced only by an explicit recheck; a failed recheck writes nothing and leaves the last metadata visible.

Scheduling and queue health

  • signal_posts is the only store of planned content. Nothing else keeps a second copy of a schedule.
  • A post carries a YYYY-MM-DD date and an HH:MM time and never an instant. No code derives a moment from the pair, which is what keeps a post on its own day in every zone. A null date is the unscheduled queue and belongs to no cell.
  • A post with no campaign is No campaign wherever campaigns are grouped, never a hidden post.
  • Acknowledging an alert writes one row to signal_alert_acks and nothing else — never a post, a publication, a target, or a planning status. It carries the fingerprint of the facts it was shown, so a situation that moves on returns as a live alert rather than staying dismissed.
  • Adding an alert kind means a rule in shared/queue-health.ts and a fixture test beside it, never a check inside a component.
No derivation beyond addition and subtraction. No rate, ratio, average, or per-post normalisation — those belong to a card that decides what they mean. A group with nothing measured carries no totals field rather than a row of zeros.

MCP connections and agent workflows

How AI coding assistants connect to this workspace, hand work to one another, and leave a trail — without any of that ever counting as the work itself.

Operator

What an agent connection is, and what it is not

This section matters only if AI coding assistants work on this application alongside a person. If that is not happening on your machine, skip to Section 08 — nothing here is needed to run the app.

An agent is an AI assistant working inside a code editor. Left alone, one of those assistants has no idea what another one is doing. Connecting them to this app gives them a governed workspace connection. Depending on the scopes you approve, they can read bounded workspace and Signal context, perform selected local writes, coordinate handoffs and leased work sessions, and request a Drive write for you to approve. Provider publishing is never exposed as an MCP write.

Making the connection is an engineer's job and it is described in the next panel. What belongs to you is the noticeboard itself — reading it, and cancelling anything that has stalled.

The words this section uses

Agent
An AI assistant that runs inside a code editor and can read and change files on its own. Cursor and Claude Code are examples.
MCP
Model Context Protocol: an agreed format that lets an AI assistant talk to another program. Connecting an assistant “over MCP” gives it a small, fixed set of actions it may perform in this app — and nothing outside that set.
Editor, or IDE
The program the assistant lives in. It is also where the connection is configured, which is why the engineer instructions below talk about editing a settings file rather than clicking anything in this app.
Label
The short name an assistant signs its work with, such as cursor-planning. Every row on the board carries one.
Handoff
One item on the noticeboard: a request passed from one assistant to another, with notes attached and a status of Open, Claimed, Completed, or Cancelled.
Inbox
The handoffs currently addressed to one particular assistant.
Local, or stdio
The plumbing used when the assistant and this app sit on the same computer: the editor starts a small helper program in the app folder and talks to it directly. Nothing crosses a network and there is no password.

Which of the two connections applies

Where the assistant runs Connection What that means for you
On this same computer Local (stdio) The normal, recommended choice. The editor starts the helper itself; you do not run a command and there is nothing extra to keep open.
On a different computer Hosted web address Only possible if this app has been published to a private web address with a login. An engineer issues a one-time key for each assistant. An ordinary install on your own machine does not have this and never will.

If someone reports that the hosted address returns not found on your machine, that is the correct answer rather than a fault. The remote door is only fitted to installations that have a login on the front of them.

Give every assistant a name you would recognise

Each connected assistant needs a label, and it should describe the job rather than the person — cursor-planning, claude-review, codex-release. It is a signature: it appears beside everything that assistant does, and two assistants sharing one label makes the board unreadable.

Labels may use letters, digits, dots, underscores, and hyphens. They must begin and end with a letter or a digit, and stop at 64 characters. No spaces.

When a client says the server failed

A local stdio client starts its own helper and stops it when the client closes. A hosted client instead shares the authenticated HTTPS service. Open Agents → Connection health to distinguish configuration, authentication, transport, and target-workspace failures before restarting anything.

Restarting one client does not affect the others, and a failed connection never harms your records — the board is read from the same database the app uses.

Reading the board: Agents → Agent handoffs

Open Agents, then Agent handoffs. You will see work that is Open (nobody has picked it up) and Claimed (somebody is on it), plus everything Completed or Cancelled in the last seven days. Open any row to read its notes.

You can cancel a stalled handoff with a retained reason and reclaim an expired work lease. The same page shows connection setup, scoped credentials, target-client verification, work sessions, the append-only agent activity trail, and pending Drive write approvals.

A handoff is a note about work, never the work. Marking one complete does not edit a task, move a planned post, publish anything, or touch Google Drive, and it is not evidence that the job was actually done. Read the board the way you would read a colleague's sticky note: it records what someone says they did.

What a connected assistant cannot do

The current registry contains 62 bounded tools across coordination, leased work, workspace tasks and projects, Signal planning, imports, settings, Drive requests, diagnostics, and read-only provider views. Capabilities are credential-scoped. There is no MCP tool that submits, updates, cancels, or retries a provider publication. Ad hoc Drive folder creation and uploads stop at an operator approval request; the separately scoped drive_sync tool can only provision standard folder skeletons.

So anything an assistant genuinely changes in your workspace, it changes the same way you would — through the app — where every ordinary preview and confirmation still stands in the way.

What is written down when an assistant acts

Every attempt to change something is recorded on this machine with three facts: which label did it, what it tried, and how it ended — succeeded, refused, or failed. Refusals are recorded as carefully as successes, so an assistant that keeps overstepping leaves a visible trail. The most recent 500 entries are kept and none of them can be edited afterwards.

The Agents page is the control room. It exposes the retained activity trail without exposing credentials or raw provider responses. Rotate or revoke a credential there, and use target-client verification after the replacement client makes a successful call.
Engineer

Local stdio connection

Add a server entry to the MCP configuration used by the client. On Windows, npm.cmd --prefix makes the repository location explicit rather than depending on the working directory the client happens to spawn from. Anchor that prefix to a variable, not an absolute path: a checkout lives at a different path on every machine, and a project-scoped config is committed.

Cursor — .cursor/mcp.json in the repository. Cursor expands variables in command, args, env, url, and headers; ${workspaceFolder} resolves to the folder containing the config. 

{
  "mcpServers": {
    "hybrid-command-center": {
      "command": "npm.cmd",
      "args": ["--prefix", "${workspaceFolder}", "run", "mcp"],
      "env": {
        "MCP_AGENT_LABEL": "cursor-planning"
      }
    }
  }
}

Claude Code — .mcp.json at the repository root. It expands ${VAR} and ${VAR:-default} but has no workspace variable, and its cwd field does not work. Fall back to . so the entry still resolves when the client is started from the repository root. 

{
  "mcpServers": {
    "hybrid-command-center": {
      "type": "stdio",
      "command": "npm.cmd",

}

Codex — ~/.codex/config.toml, which is global and has no project context, so an absolute path is correct there. That file is machine-local and never committed, so it does not need to be portable. 

[mcp_servers."hybrid-command-center"]

[mcp_servers."hybrid-command-center".env]

One label per client, not one label per repository. Each connected client is an independently running agent, so give each its own — cursor-planning, claude-review, codex-release. Two clients sharing a label makes the handoff board unreadable and the audit trail useless.
  1. Save the MCP configuration and restart or reload the IDE's MCP servers.
  2. Confirm that hybrid-command-center connects.
  3. Confirm that its tool list contains coordination_list_handoffs and coordination_post_handoff.
  4. Read hcc://coordination/inbox?state=open or call the list tool before taking work.

An MCP client may instead provide _meta.agent_label during initialize. MCP_AGENT_LABEL takes precedence when both are present. Reads work without a label; coordination writes are refused without one.

Hosted HTTPS connection

Start in Agents → Connection setup. Choose the client, assign its unique label and least-privilege scopes, then issue the one-time credential. Cursor, Claude Code, and Codex receive a client-specific ready-to-paste setup. Store the returned hcc_mcp_… value only in that client's secret storage. 

{
  "url": "https://your-hcc-host/api/mcp",
  "headers": {
    "Authorization": "Bearer <issued MCP bearer>"
  }
}

Every request sends the Authorization header. The label and scopes are bound to the credential, so do not add x-agent-label by hand; a conflicting label is rejected. Password change, session-secret rotation, credential rotation or revocation, and database restore can require a replacement credential. Verify the replacement only after that target client makes a successful call.

Claude Desktop, claude.ai chat, and Cowork use MCP OAuth instead: add only the server URL under account-level Connectors, click Connect, then sign in and approve the label and scopes in the browser. Do not paste a bearer or add request headers to that OAuth connection.

Why the passwordless runtime has no /api/mcp. Pinned by tests since 5.4.1, so a later change cannot quietly publish an unauthenticated JSON-RPC endpoint on the app's own origin without a gate turning red. The route is mounted only when operator authentication is enforced — which the ordinary passwordless local default, an incomplete checklist, never is. Note that the bind address is not the gate: a hosted AWS install keeps HOST on 127.0.0.1 behind Caddy, still enforces login, and therefore still serves /api/mcp. A passwordless local install returns 404 for POST /api/mcp and 400 for POST /api/auth/mcp-bearer. That is expected, not a misconfiguration — use local stdio instead.

Protocol methods implemented

Both transports implement the same deliberately small JSON-RPC subset: initialize, notifications/initialized, ping, tools/list, tools/call, resources/list, resources/read, prompts/list, and prompts/get, and cancellation notifications. HTTP clients may initialize a stateful session and retain the returned Mcp-Session-Id, open GET /api/mcp for SSE notifications, and end it with DELETE /api/mcp. Progress and cancellation are session-scoped. One-shot JSON-RPC POSTs without a session header remain valid.

Set MCP_AGENT_LABEL in the server entry's env block, as above. It is the only MCP-specific environment variable and it belongs to the MCP client's configuration, not to the application's .env.

Current tools, resources, and prompts

The canonical registry currently exposes 62 tools. Use tools/list and system_capabilities instead of copying a remembered list: scopes can hide tools a credential was not granted. The groups are coordination and work sessions; workspace reads and writes; Signal planning and queue health; import preview/commit; media resolution; Files browsing, Drive approval requests, and standard folder provisioning; provider inventory and analytics reads; branding/view defaults; integration activity; and diagnostics.

4 resources are available: hcc://coordination/inbox, the resumable coordination change feed, bounded hcc://workspace/context, and the resumable workspace change feed. 5 workflow prompts compose safe sequences: start_claimed_work, review_project_status, prepare_handoff, verify_before_complete, and triage_signal_queue.

Publishing stays human-confirmed. MCP can inspect planning state and build a publish preview, but no registered tool submits, updates, cancels, retries, or reconciles a provider publication. Ad hoc Drive creates/uploads stop at operator approval; drive_sync is limited to the standard folder skeleton.
Agent

The handoff lifecycle

  1. Look before claiming. Call coordination_list_handoffs or read hcc://coordination/inbox?state=open. Use coordination_get_handoff to read the full request and notes.
  2. Claim exactly one item. Call coordination_claim_handoff with its handoffId. A directed handoff can be claimed only by its named label; an any-agent item is first-claim wins.
  3. Do the real work. Follow the repository's ordinary authorization, confirmation, validation, and provider rules. A claim grants no additional permission.
  4. Leave useful evidence. Use coordination_add_note for a blocker, decision, changed assumption, file or PR reference, or validation result. Never include tokens, passwords, API keys, or raw provider responses.
  5. Close honestly. Call coordination_complete_handoff only after the requested outcome is actually achieved. If the work is obsolete or must stop, call coordination_cancel_handoff with a specific reason.

Leased work sessions

A claimed handoff can be paired with a durable work session. Start it, send heartbeats while work continues, checkpoint material progress, request operator input when necessary, and release or complete it honestly. A lease prevents two agents from silently doing the same job forever; expired sessions appear in Agents for operator reclaim. Resume context is bounded and does not turn a stale lease into proof of work.

Creating a handoff

Call coordination_post_handoff with a subject type, a concise actionable message, and optionally a target label and workspace subject ID. Use a stable clientRequestId when retrying so an ambiguous response cannot create a duplicate. 

{
  "toAgentLabel": "claude-review",
  "subjectType": "project",
  "subjectId": "42",
  "message": "Review project 42 acceptance criteria and note any unmet evidence.",
  "clientRequestId": "project-42-review-v1"
}

Subject types are task, signal_post, project, client, and freeform. Omit toAgentLabel for the open pool and omit subjectId for freeform work. The server fills fromAgentLabel from the MCP session and refuses a conflicting value.

Resume and limits. Stateful HTTP sessions can receive SSE resource update notifications. Durable resume comes from the coordination and workspace change-feed cursors, not from the notification stream. Coordination writes are capped at 10 in a rolling minute; reads do not spend that write budget.
The network write budget is persistent and credential-bound. Over HTTPS the cap is enforced two ways at once, both at 10 writes per rolling minute: an outer budget keyed on the credential alone — the bearer, or the session for cookie auth — and an inner budget keyed on that credential plus the agent label, nested inside it. The outer one is the ceiling. A credential is already bound to one label; ten a minute per credential is the whole allowance. Budgets live for the life of the server process and reset when it restarts; idle keys are pruned. Local stdio is unchanged — it keeps its own per-session limiter.

Field limits

Values longer than these are refused, not truncated: agent label 64 characters, clientRequestId 64, message 2000, coordination_add_note body 2000, cancel reason 500, and subjectId 200. A label must additionally start and end with a letter or digit and may otherwise contain only letters, digits, ., _, and -.

The inbox resource takes one form

resources/read accepts hcc://coordination/inbox?state=open, or the same URI with the query omitted. Any other state — ?state=claimed, ?state=completed — is refused rather than filtered. To read anything other than open work, call coordination_list_handoffs, which takes a state argument.

When a call is refused

Refusals are ordinary and expected; handle them rather than retrying blindly.

  • Over the write budget: the call returns Coordination write rate limit exceeded (10 per rolling minute), together with retryAfterMs — how long until the offending window has room again. Nothing is written and nothing is queued. Wait that long and try again; an immediate retry simply fails too, and switching agent label does not get you past it.
  • No agent label: reads succeed, writes are refused. Set MCP_AGENT_LABEL or send _meta.agent_label on a local initialize. Over HTTPS, issue a credential bound to the intended label.
  • Claiming someone else's directed handoff: refused. A directed item is claimable only by the label it names.
  • Already claimed: an any-agent item is first-claim wins. Re-read the row rather than assuming your claim held.
Every attempt is audited, including refusals. Each write-tool call records the agent label, the tool, and SUCCESS, REFUSED, or FAILURE to an append-only table the operator can have inspected. Never put a token, password, API key, or raw provider response in a message, note, or cancel reason — those fields are stored as written and are read by people.

Backup and recovery

One SQLite file holds every record you have entered. Treat it accordingly.

Operator

One file holds everything you have typed

Every client, project, task, checklist, tag, note, and planned post you have entered lives in a single file inside the app folder: data\command-center.db. Lose it and you lose all of it, which is why taking a copy is a two-minute habit rather than a project.

Your actual documents are not in that file. Those are in Google Drive and are backed up by Google. This file holds the records about the work.

Pending agent uploads are the exception. Until an upload request is denied, expires, or finishes, its bounded content is held in SQLite awaiting your decision. Terminal rows purge those bytes, but an older backup can still contain them. Protect and expire database backups accordingly; cleaning the live row cannot retroactively scrub a snapshot.

Taking a copy

  1. Stop the app first. Click its terminal window, hold Ctrl and press C, and wait for the > prompt to come back. Copying a database while it is being written to is how you get a copy that will not open.
  2. In that same window, run npm run db:backup.
  3. It prints Backup written to followed by the full path of the file it just made. Copies land in data\backups\ inside the app folder, named by date and time.
  4. Start the app again with npm run dev.
A copy sitting on the same computer is not a backup. The data\backups\ folder lives on the same disk as the original, so one failed drive takes both. Copy the newest file out to an external drive or a private cloud folder on a rhythm you actually keep to. It contains every client name, contact detail, and note you have entered, so store it somewhere private.

When to take one

  • Before merging two clients — that one cannot be undone.
  • Before deleting a project, which takes its tasks with it.
  • Before an engineer updates the app or opens the database.
  • On a schedule of your choosing. Weekly is a reasonable floor for active work.

The encryption key lives somewhere else

Keep GOOGLE_TOKEN_ENCRYPTION_KEY from your .env file in a different private place from the backups — a password manager, not the same folder. Restoring a database without that key gives you all your records back and no working Drive connection, and the two together in one place defeats the point of encrypting anything.

Habits worth keeping

  • Never email, upload, or share .env or the database file.
  • Never type an OAuth secret into a page inside the app. Nothing in this app will ever ask you for one.
  • Read the Google approval page before approving it, and check it names the account you meant to use.
  • Stop the app when you step away from a shared computer. Anyone who can reach the browser on that machine can reach your workspace.
Engineer

A task will not move to Complete Something it depends on is unfinished. Open the task and read Dependencies: finish the blockers, remove one that is wrong, or use the override deliberately.
A dashboard count looks wrong Check the task has a due date, is not already Complete, and sits under the project you think it does. Then check this computer's own date, time, and timezone — the counts are worked out from them.
Something not on this list Copy the whole message from the terminal, note what you did immediately before, and send both to an engineer. A screenshot of the last line alone is rarely enough to work from.
Engineer

Diagnosing past the obvious

  • Config failures are reported all at once at boot, by variable name, never echoing the rejected value — terminal output is safe to paste into an issue.
  • Moving PORT requires matching changes to the OAuth redirect URI and the dev proxy. Prefer closing the duplicate process.
  • A seven-day Drive dropout is almost always the External-app-in-Testing refresh token expiry, not a bug in the token store.
  • Raise LOG_LEVEL to debug or trace for a run; anything unrecognised falls back to info.
  • Set APP_ORIGIN to the scheme-included origin the API should answer for CORS.

Changing the code

Branch naming, the draft-then-finalize release path, and what "done" means here.

Engineer

Branches, versions, and gates

Branch from main, one card per branch, named <type>/<issue>-<slug>. Types are feat, fix, chore, and docs. Settle the branch name before opening a pull request — renaming a head branch closes the PR and it cannot be reopened once the old ref is gone.

Required checks: npm run typecheck, npm run lint, npm run format:check, npm run build, npm run test:coverage, and npm run test:e2e. CI runs the coverage variant, so a drop below any threshold fails the build.

Coverage thresholds are measured figures, not targets. Raise one when the suite genuinely covers more. Never lower one to make a branch pass.
Agent

Do not claim a version while under review

Every merged card ships a version bump, but feature work must not claim one early. Keep the pull request draft and add one fragment at changes/<issue>.md instead of editing CHANGELOG.md, package.json, package-lock.json, or shared/branding.ts. One file per card means concurrent cards do not conflict.

Never name a branch after a version number. The version is decided at merge time from milestone close order — first card closed takes the minor bump, the rest take patches — so it is unknowable when the branch is created.

Finalization, in order

  1. Refresh origin/main and merge or rebase it into the branch.
  2. Reread the issue's bump rule and take the next available version.
  3. npm version <new-version> --no-git-tag-version, and set APP_VERSION in shared/branding.ts to the same value.
  4. Move the fragment's content under a new dated heading at the top of CHANGELOG.md, then delete the fragment.
  5. Run npm run check:version-bump and every required gate, then mark ready and merge.

If another card lands first, repeat finalization against the new origin/main. Never preserve a now-taken number.

Marking ready too early now self-heals. Clicking Ready for review the moment the draft-time checks go green — before running the finalize steps above — makes check:version-bump fail deterministically, and no code change can fix it. Since 5.4.3, CI stops leaving that as an unexplained red check: on exactly that failure it converts the pull request back to draft and comments with the finalize checklist. Nothing in the running application changed; this is a contributor-workflow guard. Finish finalization, then mark ready.
The strip-types trap. The server runs under node --experimental-strip-types, which erases annotations without rewriting code, so constructor parameter properties do not work there. Declare the field and assign it in the constructor. Vite transpiles them, so unit tests, typecheck, and the build all pass while the real server refuses to boot — @typescript-eslint/parameter-properties is enforced over server/ and shared/ so lint catches it instead.

Definition of done

The user flow is complete, validation and error states are present, unit and integration tests pass, TypeScript and lint pass, the production build succeeds, responsive behaviour is preserved, and no secret or real-Drive side effect is introduced. Every gate in .github/workflows/quality-gates.yml blocks the merge, end-to-end included.

Every milestone adds at least one e2e/ spec — not every card, a milestone. Cover the flow the milestone was about, in one spec, end to end; leave branches and error paths to unit tests.

Changelog entries say what changed for someone using the app, not which files moved. State breaking changes explicitly, including their absence, so a major digit is never left to be inferred.
